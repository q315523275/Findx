Findx.Extensions.Scheduler · V3 · 2026-11

Findx 分布式调度架构说明

调度端与执行端彻底分离：调度端只依赖 MySQL 与 HTTP，执行端零数据库连接，全部通过协议通信。 不引入 Redis、消息队列、注册中心；正确性由数据库 CAS 与唯一键保证，中间件能力全部收敛为接口，后续可按需替换实现。

数据源 jobs（MySQL） 机器间协议 HTTP 调度端 / 执行端 同进程可分离 至少一次投递 失败退避 → 死信隔离 执行日志：明细 + 摘要

1设计概览

为什么去 Redis：不是嫌它快，而是"在途执行只活在 Master 进程内存"——换主即丢。

关键路径只依赖 DB + HTTP

选主、领取、投递受理、结果终结、心跳、日志，全部落在四张表与五个 HTTP 接口上；不引入额外中间件，部署即"两个服务 + 一个库"。

中间件能力接口化

IMasterLease / IPeriodClaimer / IExecutionLedger / IWorkerDirectory / IExecutionLogStore 收敛为抽象，换 Redis/etcd 只替换实现，调度链路代码不动。

正确性由 CAS 与唯一键保证

租约只减少无效扫描，不承载正确性；"同一周期不重复触发"由任务行 CAS + 执行行 ExecutionKey 唯一键共同保证。

与内存版 Jobs 的关系

同一套 IJob 与 JobExecuteContext，由 Findx:Jobs:ScheduleType 决定内核：Simple 走内存版（单机、无账本），Distributed 走本组件（多节点、DB 账本）。组件启动时强制校验二者互斥，避免双内核同时点火。

一句话定位：把「什么时候跑、谁来跑、跑完没有」三件事全部落到数据库账本上；进程只是执行者，不是状态持有者。

2架构总览

左：调度端（租约唯一，1 主 N 备）· 右：执行端（N 节点，各自承载不同 IJob）· 下：唯一协调介质

三方职责

角色职责不负责
调度端选主与租约、到期扫描、预取、周期领取、能力匹配投递、结果收敛、超时兜底（独立节拍）、日志落库、历史清理、管理面不执行任务本体；不因为持有租约而获得"唯一触发权"
执行端心跳与能力注册、受理入队、并发执行、日志采集与分片上报、结果回调不决定"何时该跑"；不直接改任务调度状态
MySQL唯一事实来源：租约、节点能力、执行账本、日志明细不做业务计算；不承载调度逻辑

调度端与执行端是同一组件的两个开关（SchedulerEnabled / WorkerEnabled），可同进程部署，也可大小节点分离；纯调度节点收到 execute / kill 一律 503，纯执行节点收到 beat / offline 返回 503。

部署拓扑示例

典型形态：两台 纯调度节点同构部署、都开 SchedulerEnabled，谁当主由 scheduler_master 租约决定，备节点待命并在主机失联 15s 内接替；执行节点按业务拆分（引物、测序、报表各一台），各自只注册自己部署的 IJob，调度端按 HandlerType 精确匹配后再投递——部署错任务不会"跑到别的机器上"。只有调度节点连库（租约、账本、日志明细都在调度端写）；执行节点不注册任何数据库原语、没有数据库连接，心跳 / 结果 / 日志三件事全部经 ISchedulerMasterChannel 协议上送（当前 HTTP，可换 RPC）。不引入注册中心或消息队列。

最少部署：1 台机器同时开 SchedulerEnabled 与 WorkerEnabled 即可跑通全部链路；扩到多台时只需复制节点并打开对应开关，账本与日志不需要迁移。

3一次触发的完整链路

从"到期"到"收敛"，每一步的观察点都能在表里查到

  1. 到期扫描DistributedScheduler 每 5s 扫 NextRunTime <= now；预取窗口 60s、30s 刷新，失败重试到期优先。
  2. 候选预检按 HandlerType 精确匹配存活节点能力；无节点时 DeferCycleAsync 只推周期锚点，不建执行行、不消耗重试次数。
  3. 周期领取（单事务）任务行 NextRunTime CAS + 插入执行行同一事务提交；ExecutionKey = jobId:period:attempt 唯一键兜底，同周期只有一次领取能成功。
  4. 投递POST /api/scheduler/jobs/execute，执行端入队即返回 202；队列满返回 503 → 未受理，按退避回写。
  5. 受理确认MarkDispatched：仅当状态为 Claimed 时 Claimed → Dispatched；未受理则 Claimed 30s 后由兜底转 Failed。
  6. 执行执行队列并发 8；每条执行开 AsyncLocal 日志作用域并注入 context.LogRecorder。
  7. 日志分片上报每 50 条切一片 → 有界队列 → 攒批 20 片 / 2s → POST /api/scheduler/jobs/logs → 明细表逐片追加。
  8. 结果回调POST /api/scheduler/jobs/result（失败退避 3 次），带 Message 与日志尾部摘要；服务端 CAS 终结，重复回调只有一条成功。
  9. 收敛成功：TryCount 归零、LastRunTime 更新、NextRunTime 推向下周期；失败：指数退避后 RetryAtTime；用尽：任务转 Dead 待人工放行。
关键取舍：投递是"至少一次"，不是"恰好一次"。业务侧若需严格幂等，用执行行 ExecutionKey 做业务侧去重键，而不是指望调度层不重发。

时序图：扫描 → 投递 → 执行 → 日志 → 回调

注意顺序：先插入执行行再投递（否则投递成功却无处记账）；结果回调前先补发最后一片日志（否则明细可能缺尾）；CAS 终结先于重试决策（否则重复回调会重复退避）。

4执行状态机

执行行 5 个状态 + 任务行 3 个状态；超时、kill、重试与死信都在图里

迁移触发条件与结果
Claimed → Dispatched执行端受理成功条件更新 State = Claimed；影响 0 行说明已被别人处理
Claimed → Failed超过 ClaimTimeoutSeconds（30s）视为未送达；不重试本次，走任务级退避
Dispatched → Succeeded回调 IsSuccess=trueCAS 终结；写 Message/JobLog/耗时
Dispatched → Failed回调失败 / 超过 ExecutionTimeoutMinutes（10min）超时由兜底扫描读表发现，不依赖执行端在线
→ Cancelled管理面 executions/kill先终结再通知执行端取消；后续回调全部被 CAS 挡掉
Failed → 新执行行任务退避到期attempt+1、新建 TraceId，最多 MaxRetryCount=5 次
任务 → Dead重试次数用尽不再自动触发；只能 release 人工放行

5数据模型

四张表 = 租约、节点能力、执行账本、日志明细；唯一键与索引必须显式建

scheduler_master · 租约

LockKey / Owner / LeaseUntil。抢租约与续期是同一条条件 UPDATE：持有者是我，或原租约已过期。

scheduler_worker · 节点 + 能力

NodeName / Address / Capabilities(JSON 任务清单) / LastHeartbeat。心跳带清单，TTL 45s 判活。

scheduler_execution · 账本

TraceId(uk) / ExecutionKey(uk) / State / WorkerAddress / DispatchAt / FinishAt / ElapsedMs / Error / Message / JobLog摘要。

scheduler_execution_log · 日志明细

TraceId + Sequence 分片追加；Content(mediumtext) / IsFinal；idx(TraceId, id) 游标分页。

必备索引（不做自动建，必须执行 DDL）

索引用途
uk_exec_trace (TraceId)回调幂等定位（按 TraceId 精确取一次执行）
uk_exec_key (ExecutionKey)同周期同尝试唯一，重复领取插入直接失败
idx_exec_state_dispatch (State, DispatchAt)超时兜底扫描（Claimed / Dispatched 两段）
uk_worker_id (WorkerId)心跳 upsert
idx_log_trace (TraceId, id)执行日志明细分页

建表脚本：docs/sql/scheduler_v2.sql；组件首次运行会按实体自动建表，但唯一键/索引不会自动建。

6机器间协议

全部 HTTP + JSON；共享令牌 X-Scheduler-Token（ClusterToken）必填

方法路径说明
POST/api/scheduler/jobs/execute调度端 → 执行端投递；入队即 202，队列满 503，纯调度节点 503
POST/api/scheduler/jobs/kill取消在跑执行（管理面先终结执行行，再调用本接口）
POST/api/scheduler/jobs/result执行端 → 调度端回调；含成功标志、Message、耗时、日志尾部摘要
POST/api/scheduler/jobs/results执行端 → 调度端批量回调；多条合并成一次请求，调度端逐条按 TraceId 幂等终结
POST/api/scheduler/jobs/logs执行日志分片（≤64 片/请求，需 SchedulerEnabled）
POST/api/scheduler/workers/beat心跳 + 节点地址 + Capabilities 任务清单（60s 重扫）
POST/api/scheduler/workers/offline优雅下线：主动摘除能力，不再接受投递
鉴权是硬要求：ClusterToken 为空时组件直接启动失败。否则 execute 等于"内网任意客户端可触发任意 IJob"。

8执行日志

Job 主动记录 + ILogger 旁路采集；量大走队列，不占结果回调

两个写入入口

context.LogRecorder.Info/Warn/Error（业务语义，不依赖日志级别）；以及组件注册的 ExecutionLogProvider 对 ILogger 旁路采集（不替换 NLog/控制台）。

为什么走队列

一次执行可能上千行日志：不能塞进结果回调（体积/延迟不可控），也不能同步等 HTTP（拖慢任务）。队列 + 攒批把网络抖动挡在执行路径外。

参数值含义
环形缓冲300 条供结果回调携带尾部摘要，内存有界
单条上限800 字符超长截断，避免单行爆炸
分片阈值 / 单片上限50 条 / 8000 字符长任务日志边跑边可见
LogShipQueueCapacity4096有界队列，满时丢最旧，不反压执行
LogShipBatchSize / LogShipIntervalMs20 片 / 2000ms同一次执行的多片合并成尽量少的请求
MaxExecutionLogChars20000结果回调里的摘要上限；明细表保存全量
LogMaskingEnabled / LogMaskPatternsfalse / 空可选脱敏（密码/令牌/Bearer/手机号/身份证 + 自定义正则）

失败处理：单地址重试 2 次后丢弃并计数，不回灌队列、不影响任务结果。进程崩溃时未发送的分片丢失（已落库的保留）。`new Thread` / 外部队列里的日志不在 AsyncLocal 作用域内，不会被采集。

9重试 · 死信 · 超时兜底

三者都不是"进程内存里的定时器"，全部是可被任何节点读表接管的持久状态；两段超时兜底由独立的 TimeoutSweepService 按 30s 节拍跑，不占用 5s 调度扫描

机制参数行为
失败退避RetryBaseDelayMs=1000、RetryMaxDelayMs=60000、MaxRetryCount=51s→2s→4s→8s→16s→60s 封顶；写 RetryAtTime，到期由扫描重新领取
死信隔离DeadLetterEnabled=true重试用尽转 JobStatus.Dead，停止自动触发；只能 release 人工放行
无节点延后DeferCycleAsync只推 NextRunTime 锚点 + LastRunTime，不建执行行、不计重试（避免同一周期执行两次）
领取超时ClaimTimeoutSeconds=30兜底扫表把 Claimed 转 Failed，再走退避
执行超时ExecutionTimeoutMinutes=10兜底扫表把 Dispatched 转 Failed；执行端离线也能收敛
回调重试3 次退避回调全失败时由超时兜底接管（该次日志可能缺失）

11性能与容量（实测）

1 调度端 + 4 执行端 + 8 分发线程 + 领取批量 50 + 在飞 64 + 采样 40s；容量参数全部走自动推导（8 核）。

下发不是瓶颈

5000 条/波，下发延迟 p50 0.375s / p95 0.631s，分发队列饱和 0 次，波次完整 4×5000。

执行端是物理上限

吞吐 ≈ 线程数 × (1 / 单条耗时)。16 线程 4096 队列在 0ms 档零拒收；50ms 档开始出现容量边界（720 次）。

回写曾是最后一环

结果上报串行时一批 20 条要 342~660ms；改成 4 路并发后，5000 档完成率从 64.9% 升到 93%+。

固定「5000 条/波、单条 50ms」，只改执行端配置。吞吐 ≈ 线程数 × (1 / 单条耗时)，是物理上限。

压测本身就是 10 秒周期任务：5000 个任务 × 每 10 秒 = 持续 500 次/秒。

扫描节拍SchedulerScanIntervalSeconds = 1，按整秒栅格对齐；:00 到期正好落在栅格点，相位偏差为零
最小粒度1 秒（受扫描节拍约束）。扫描间隔不要调大，否则 */3 这类会跨栅格丢波
实测节奏500 次/秒：完成率 98.3%、下发 lag p50 0.375s / p95 0.631s、整批回滚 0
切换空窗默认 CatchUpWithinWindow=false 只补当前一次，Master 接管 15~20s ≈ 丢 1~2 个 10 秒波
真正的约束是在途量，不是周期： 每秒下发量 × 单条业务耗时 ≤ 执行端总线程数。500/s × 50ms = 25 并发（4 端 × 16 线程 = 64，宽裕）； 同样 500/s 配 200ms 业务就是 100 并发，开始排队靠队列缓冲，lag 抬到 0.6s 量级——这是「50ms 档完成率落到 86.9%」的机制，不是调度能力不足。

要容忍切换丢波：打开 CatchUpWithinWindow=true，上限 CatchUpMaxCount=30（10 秒任务最多补 5 分钟）。 想做到 1 秒一发：扫描栅格本身是 1 秒，边界内可行，但 5000 任务 × 1 秒 = 5000/s 是已验证 500/s 的 10 倍，属于未测区，正式使用前需按同一口径重跑。
容量定位：目标是「单波 5000、保有量 5 万」。超过这个量级需重新评估， 容量预案见压测报告第十五节（多主分片：暂不实施，因为分片只能扩调度端、扩不了共享的 MySQL）。

12不变量与边界

哪些是承诺，哪些是明确不承诺

不变量

  • 同周期同尝试只有一行执行记录：ExecutionKey 唯一键是最后防线。
  • 重复回调只有一条能终结：CAS 更新 WHERE State NOT IN (terminal)。
  • 租约不承载正确性：租约抖动最多多一轮空扫描，不会重复触发。
  • 换主不丢在途：兜底扫描读执行表，任何节点都能接管。
  • 死信真停机：Dead 不会自动恢复，需人工 release。
  • 单条键冲突不连坐：领取写入前按 ExecutionKey 查重，命中的只剔除该条，其余同批照常提交。

明确不承诺

  • 不做"恰好一次"：投递为至少一次，业务幂等请用 ExecutionKey。
  • 不做长连接 RPC、调度端与执行端双进程强绑定、广播分片。
  • 不做多主分片：当前是一主一备，单 Master 调度；超过容量目标再启用预案。
  • 主备切换有 15~20s 空窗，空窗内到期的触发默认不补（CatchUpWithinWindow=false）。
  • 不做可视化前端与 DAG 依赖编排（管理面只提供 API）。
  • 不做执行日志全量归档：超过 RetentionDays 与账本一并物理删除。
  • 进程崩溃时，尚未发送的日志分片会丢失；已落库的分片保留。
  • Job 自行 new Thread 或投递到外部队列后执行的日志不在采集作用域内。
扩展方向：实现 IMasterLease / IWorkerDirectory 等接口即可把协调介质换成 Redis / etcd / ZK，调度链路与业务 IJob 无需改动；日志与账本也可按同样方式替换存储。
