Findx.Extensions.Notify · 2026-11

Findx 消息通知组件架构说明

一个 INotifySender 出口，把同一份内容发到企业微信、钉钉、邮件、公众号、小程序。 业务主流程默认零 IO：QueueAsync 只做对象构造与一次 TryWrite，发送与落库都在后台线程。 通道按配置注册，未启用的通道不会被注册——不存在「已启用但参数没配」的半可用状态。

单出口 INotifySender IUserNotifier 通用契约 五个通道 业务线程零 IO 队列满降级同步 日志一次 INSERT

1设计概览

三个决定：为什么是单出口、为什么默认异步、为什么日志只写一次。

单出口，而不是每通道一个客户端

路由、超时、异常收敛、日志、广播都只写一份。业务只依赖 INotifySender； 审批、调度等组件只依赖核心包契约 IUserNotifier，由本组件决定落到哪些通道。

默认异步，同步是例外

通知不属于业务事务的一部分。主流程里做 HTTP 往返会把通道抖动放大成业务延迟； QueueAsync 只入内存队列，毫秒级返回日志 Id。只有「必须立刻知道成败」才用 SendAsync。

日志是「发送事实账本」

先 Apply 结果再一次性 INSERT，没有「发送中」行、没有二次 UPDATE。 代价是：在途消息无法从库观测，进程崩溃时队列里的消息与尚未写入的日志一起消失。

一句话定位：这是一个「进程内异步发送器 + 发送事实日志」，不是可靠消息队列。 它保证「每条调用的结果可解释、可反查」，不保证「消息一定送达」。

2组件架构

装配 → 调用方 → 门面 → 分发 / 队列 → 通道 → 外部平台 → 日志表。

职责边界

角色职责不负责
NotifyModule按 Findx:Notify 注册通道、分发器、队列、日志存储；把 IUserNotifier 替换为同一实例不做发送，不做重试
NotifySender同步发送 / 异步入队 / 多通道广播 / 契约字段映射；同步路径落库不解析通道协议，不重试
NotifyChannelDispatcher按 Channel 查表路由、统一超时、异常收敛为 NotifyResult.Fail不做重试与降级决策
NotifyDispatchQueue有界内存 Channel + N 个消费线程；发送、回填、落库不持久化，不保证停机后仍在
INotifyChannel协议组装 + 平台返回码翻译（企业微信 / 钉钉 / 邮件 / 公众号 / 小程序）不管超时（上层统一给）
NotifyLogStore一次 INSERT 写 notify_logs；失败只记 Warning不影响发送结果，不重试写库
装配的关键点：通道按 Enabled 决定是否注册。未注册的通道不会进 dispatcher 字典， 调用时返回「通道 X 未启用：请配置 Findx:Notify:X:Enabled=true」，而不是发出一个参数缺失的请求。

3两条发送路径

谁承担网络耗时，决定了结果何时可知；每个分支都有确定结果。

方式调用线程开销返回适用
QueueAsync对象构造 + 一次 TryWrite，无网络、无数据库long 日志 Id（入队前已生成；0 = 消息为空）业务主流程中的通知（推荐）
SendAsync一次 HTTP / SMTP 往返（≤ TimeoutSeconds）+ 一次 INSERTNotifyResult必须立刻知道成败
广播 SendAsync(channels, message)逐通道并行，各自独立结果与日志IReadOnlyList<NotifyResult>同一内容多通道兜底
队列满不丢消息：TryWrite 返回 false 时，本次降级为在调用线程同步发送， 仍返回同一个 log.Id。代价是这一次调用变慢；换来的语义是「入队失败 ≠ 消息丢失」。

4通道矩阵与日志模型

每条通道只做协议组装；日志表记录发送事实。

日志字段怎么用

  • Id：入队即生成（IKeyGenerator），业务可以在发送前就拿到并写入自己的业务表。
  • BusinessKey：单据号 / 流程实例号，落到日志后可按业务反查「这条单据发过哪些通知、结果如何」。
  • Payload：完整消息 JSON 快照。ToMessage() 优先用它还原，损坏时回退到列字段重建。
  • ElapsedMs / SendTime：异步路径的 CreatedTime 是入队时刻，两者相减即排队延迟 + 发送耗时。
  • NodeName：多实例部署时定位是哪个节点发出的。

5配置项

配置节 Findx:Notify；各通道 Enabled 默认 false。

配置默认语义
Enabledtrue组件总开关；关闭后所有发送返回 Fail（可读原因）
DefaultChannels[WeCom]通过 IUserNotifier 发通知时广播到哪些通道
TimeoutSeconds10单次发送上限，dispatcher 用 linked CTS 取消
LogEnabledtrue关闭后两条路径都不写 notify_logs
NodeName空写入日志，用于多实例定位
QueueCapacity2048内存队列容量；满时降级同步发送
DispatchWorkerCount2后台消费线程数
WeCom.WebhookUrl / CorpId+Secret+AgentId—群机器人（优先）或应用消息
DingTalk.WebhookUrl / Secret—群机器人，可选加签
Email.IsBodyHtmltrueSMTP 参数复用框架 Findx:Email
WeChat / WeChatMiniProgram 的 AppId+AppSecret+TemplateId—模板消息 / 订阅消息；小程序另有 Page、MiniProgramState、Lang、TruncateTooLongValue

6不变量与边界

成立的不变量

  • 每条 NotifyResult 都有明确通道与可读原因；通道异常已被 dispatcher 收敛，不向业务抛出。
  • 未启用的通道不会被注册，也不会发出参数缺失的请求。
  • 队列满时消息仍然被发送（降级同步），不会静默丢弃。
  • 日志落库失败不影响发送结果与业务线程。
  • 同一 NotifyLog 只 INSERT 一次，落库时已是终态。

边界（现状即如此）

  • 没有重试：通道失败只写 Failed 行 + Warning，不自动重发；重发要业务侧用 Payload 重建。
  • 没有持久化队列：进程崩溃时队列中未发送的消息丢失（已落库的日志行保留）。
  • 广播是并行不聚合：单通道失败不影响其它通道，但调用方看到的是逐个结果，需要自行汇总。
  • 公众号 / 小程序逐条发送：To 有 N 个 openid 即 N 次 HTTP，不是批量接口。
  • 在途不可观测：没有「发送中」行，也没有队列深度指标（只有进程内计数）。
若要把「不丢 + 可重试」补齐：需要把 QueueAsync 换成「先落库再消费」的持久化队列 （或复用调度组件的 DB 账本思路：入队写行、消费 CAS 认领、失败退避、终态归档），而不是在内存队列上加循环重试。
