01 同一负载下的实际到位率 到不了的，是被静默丢掉的

"到位率" = 执行端实际收到的触发数 / 该时段应触发数。xxl-job 的丢调度不会写进业务日志表，只会以 schedule misfire 警告出现，很容易在线上被忽略。

05 差距不在代码量，在模型

xxl-job：调度与记账串在同一条线程

  1. 单个 scheduleThread 每轮预读 ≤6000 条到期任务
  2. 对每条：insert 一行日志 + update trigger_next_time
  3. 把任务塞进秒级时间轮，由 ringThread 到点取
  4. 投递到 fast/slow 线程池（200/100 线程，队列 1000/2000）
  5. 队列满 → RejectedExecutionException；过期 >5s → misfire 直接跳过
500 条耗时约 1.5s ⇒ 约 3ms/条，与并发度无关。这条串行链就是它的吞吐上限。

Findx：投递并发，记账批量

  1. 内存窗口比对到期，没有逐 job 的 update
  2. 节点目录走倒排字典，O(1) 选点、零分配
  3. 投递并发执行，受全局在飞闸门（默认 64）约束
  4. HttpClient 单例复用，单次往返降到毫秒级
  5. 受理项收齐后 MarkDispatchedBatchAsync 一次批量记账
代价是 DB 写更多（约 10.5 SQL/执行，5000 档 ≈5200 QPS，是它的 1.7~2 倍），换来账本与幂等。

3.0 把这条串行链拧紧了一档：官方 changelog 里对应的是时间轮单刻度去重 + 转动时校验临近刻度、 快慢线程池默认配置上调、预读任务数计算系数下调（降低事务颗粒度）、锁逻辑与事务 SQL 下沉。 结果是 200 次/s 从"丢一半"变成"几乎全发"，但 scheduleThread 仍然要一个人干完「预读 + 逐条记账 + 推时间轮」，所以 500 次/s 的持续负载上，队列一满就是 execute too fast（我们这轮采到 2794 次），过期一超就是 misfire（5000 条/轮）。缓冲池解决不了并行源的问题。

06 读这组数据前必须知道的五件事

  1. 硬件不对等。xxl-job 官方镜像只有 linux/amd64，本机是 arm64，它跑在模拟层上；我们是原生 arm64。按 3ms/条 折回原生 x86，它的上限大概能到 500~800 次/s，这个差距会明显收窄。
  2. 执行端数量不对等。它接 1 个假执行端，我们接 4 个 worker。这只影响执行侧，不影响"调度线程能否跟上到期速率"这个判断。
  3. 它只起了一个调度中心。xxl-job 支持多实例靠 xxl_job_lock 行锁分摊，本实验没开多实例——这是它真实的水平扩展手段。
  4. 负载形态是故意选的极端。全部任务同一秒到期，是它最不擅长的形态；官方"5000 任务"的口径是混合周期。所以 2000/5000 两档说明的是"扛不住同相位全量一波"，不能读成"只能带 2000 个任务"。
  5. 它的丢调度是静默的。不写业务日志表、不报失败，只打 schedule misfire 警告。这在线上比"慢"危险得多。
